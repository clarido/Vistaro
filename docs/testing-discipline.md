# Test discipline

These rules apply to every agent and every person changing this repo (Claude Code, Codex, GLM). AGENTS.md is the manual for *driving* the CLI; this file (`docs/testing-discipline.md`) is the manual for *changing* it.

## The rules

1. **Every bug fix ships with a test that fails first.**
   - Write it from the real artifact that triggered the bug (the actual `anim.config.json`, mockup, MP4 or HTTP request), reduced to its shape, with no client content.
   - Run it red on the unfixed code, then green on the fix, and say both in the commit or PR.
2. **Every invariant written in AGENTS.md or here gets a canary test, or it isn't real.** A canary scans the codebase for a whole class of mistake, so it catches the next person who never read the rule. Each rule in the inventory below names its canary, or says « no canary yet ».
3. **A canary only counts if it can fail.**
   - Its oracle is independent of the code under test, and uses the same accessor its consumer uses, not a look-alike that agrees today.
   - Assert an identity (this exact element or file), never a class (« not empty », « status != x »).
   - Its self-test goes red when discovery finds nothing: if a rename makes it scan zero files, it fails rather than passing.
4. **Mutation check for every new test.**
   - Break the code it guards (`if (false && …)`, remove the guard, invert the condition), watch the test go red, then restore.
   - Back the file up with `cp` before mutating. Never `git checkout` a file that has uncommitted work.
   - After any change to a test, replay every mutation it had killed: a test-only fix can resurrect one.
5. **Don't write a test and the code it tests in the same breath and call it verified.**
   - Prefer the real thing: a real Chromium, a real ffmpeg encode, a real HTTP call to `saas/server.js`.
   - Mocks hide exactly the bugs this tool has (timing, injection, encode).
   - Run anything that writes state (a `build-all --changed-only`, a SaaS job, a live-page `record` with `reset`) twice: idempotence bugs only appear on the second run.
6. **A failed or contended run is not a result.**
   - Browser and ffmpeg tests are machine-sensitive (see AGENTS.md, Contributor notes), so rerun a red test alone, on an idle machine, before acting on it.
   - One browser-driven job at a time.
7. **Report exit codes, not impressions.** Read each command's exit code in its own call. Give the suite's counts (pass, fail, skipped) before and after. Say plainly what you could not verify.
8. **Loosening a guard, a canary or an allowlist needs JF's explicit go.** That covers adding an exception, widening a pattern and raising a ratchet.

## When a canary goes red at you

1. **A red canary is a finding about your change, never an obstacle.** Never silence it — no skip, no deleted assert, no weakened oracle, no narrower scan: making the canary green without making the code carry the invariant is the exact mistake it exists to catch.
2. **Read the failure message: it names the file and what is missing.** You broke the invariant → change your code to carry it. You added a legitimate new site → adopt the prescribed pattern and extend the canary's list (`KNOWN_SITES`) in the same change; the list is an identity, not a quota. `test/spawn-bounds.test.ts` going 12 → 13 sites is this rule in action.
3. **If the canary itself is wrong**, fixing it is its own change: say why the oracle is wrong, fix it, and re-prove it can fail (plant the violation, red, restore).
4. **Loosening — accepting a different bound-shape as equivalent, widening a pattern or window, an allowlist exception, a raised ratchet — is JF's explicit go, typed by JF, never relayed** (rule 8). Extending a list by adopting the prescribed pattern is not loosening; that is the designed path.
5. **Before READY, run the canaries whose scope you touched** (they are static scans, seconds): a spawn added → `test/spawn-bounds.test.ts`, `test/src-spawn-bounds.test.ts`, `test/src-async-spawn-bound.test.ts`; `runtime.js`/`tour-bridge.js` → `test/plain-browser-js.test.ts`; `cli.ts` → `test/docs.test.ts` + `npm run docs:check`; package.json scripts → `test/serial-suite.test.ts`; workflows → `test/ci-workflow.test.ts`; hooks, `.githooks/claude/settings.example.json` or `.githooks/pre-push` → `test/guardrails.test.ts`. The full suite is the landing gate's job, not the coding loop's.
6. **A red naming a file that is not yours is a cross-lot event:** report it to the coordinator; never fix foreign work to make your own gate green.
7. **When you write a canary**, its failure message must tell the next coder what to do (house model: `test/spawn-bounds.test.ts`), it must go red on empty discovery, and its inventory row updates in the same change.

## Working in lots (more than one session on the tree)

JF runs several agent sessions against one checkout of `main`. When more than one codes at once:

1. **Lots, not piles.** One coherent change per lot, an explicit cleared file list before any code is written, and JF's `/docommit` at each landing. Nothing commits without his word, and every commit names its paths.
2. **The coordinator** — whichever session JF tasks with it — clears file lists against the open lots and the dirty tree, sequences the heavy jobs (one browser-driven job at a time), verifies every landing, and reports to JF in English, by tab. It never codes a lot, never lands one, and never relays a go.
3. **A dirty file you did not touch belongs to someone else.** Name it and leave it; your commit's pathspec must not carry it. A canary red naming a foreign file is a cross-lot event (§6 above).
4. **JF's calls alone, never relayed:** pushes, the guardrails' ACTIVATION, any rule-8 loosening, anything paid.
5. Coordination state lives in .zcode/coordination-state.md — session machinery, never committed, and named in prose on purpose: the docs quote only what the repo ships.

## ACTIVATION

The guardrails ship inert, and switching them on is JF's, not an agent's — from that moment every tab's behaviour changes, which is exactly why no `.claude/settings.json`, no `core.hooksPath` and no npm wiring script ships in the repo. The two one-liners:

```bash
# 1. Wire the pre-push fast tier into git (repo-local; no --global):
git config core.hooksPath .githooks
# 2. Activate the Claude Code guardrails (this and every future tab; .claude/ may not exist on a fresh clone):
mkdir -p .claude && cp .githooks/claude/settings.example.json .claude/settings.json
```

The first turns on the pre-push tier: every push from this clone then runs tsc, docs:check and the twelve static canaries before the ref leaves — never the suite, which stays CI's landing gate. The second turns on the Claude Code guards for this and every future tab: the Bash guard on every Bash call, the whole-project typecheck after every TypeScript edit. Each switches off on its own: `git config --unset core.hooksPath`, `rm .claude/settings.json`. `test/guardrails.test.ts` watches the shipped files before AND after activation — post-activation it asserts the live file equals the example, so a drifting copy reds the canary instead of quietly switching a guard off. Loosening a deny pattern, an ask list or a timeout budget is rule 8: JF's explicit go, typed by JF, never relayed.
